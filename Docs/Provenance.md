# Происхождение кода и описаний

## Исходные байты

Все семь логических файлов, служебная дорожка, дополнения последних секторов
и свободная область извлечены из пользовательского `ELITE3HL.TRD`.
Машинный код другой версии не подставляется в собираемый проект.

Текущие уточнения имён, полей и битовых схем выполняются только по инструкциям,
записям и чтениям данного TRD. Elite Legend не используется как основание
этих описаний. Упомянутые ниже прежние сопоставления сохраняют историю анализа
и сами по себе не доказывают назначение поля или процедуры целевой версии.

Первичное основание разбора — инструкции этого диска после обратимого
XOR-преобразования. В исходном представлении сохранены начальные шесть байтов
генератора, поэтому оно не тождественно всей RAM после загрузки. Для алгоритма
загрузчика отдельно сопоставлены модель на Python и исполнение оригинальных
инструкций Z80.

## Что использовано из Elite 128K

Справочный файл
[`elite128.skool`, nzeemin/LW](https://github.com/nzeemin/skoolkit-game-revs/tree/master/elite128-zx)
использовался для поиска соответствий:

1. Имена процедур, например `PrnCockpit`, `EnergyRecovery`, `UseEscapePod`.
2. Кандидаты на точки входа, границы фрагментов и адреса данных.
3. Предположения о назначении алгоритмов, проверяемые затем по целевому коду.

`Tools/Disasm/Research/MatchReference.py` сравнивал окна из десяти инструкций. При поиске
игнорировались абсолютные операнды RAM `#4000..#FEFF`, но сохранялись остальные
константы, длины команд и относительные смещения переходов.
Найденные последовательности продлевались и сопоставлялись по связям вызовов.

Исторический результат в `Tools/Disasm/Reports/ReferenceMatches.json` содержит
241 совпадающий участок, 367 кандидатов процедур и 186 кандидатов меток данных.
Из 367 процедур алгоритм пометил 134 как `supported`, 233 как `candidate`.
Даже `supported` в этом файле означает поддержку структурного сопоставления,
а не подтверждённость всего смыслового описания.

Эта первоначальная карта сохраняется для проверки происхождения гипотез.
Она не является итоговым реестром завершённости. Шаблонные пояснения
первоначального экспорта также не считаются ручным разбором.

Для сопоставления геометрии ранее дополнительно просмотрены внешние исходники
`EliteLegend_v1_09_source/INCLUDE/Ships`. Это справочный идентификатор прежнего
сопоставления, а не путь к зависимости проекта. Совпадения координат
перечислены в `Tools/Disasm/Reports/ModelGeometry.json`. Они помогают выбрать аналитические
имена моделей, однако формат потоков, поля заголовков и потребители проверены
по этому TRD. Имена Fighter1/Fighter2 сохраняют нейтральное обозначение,
названия Taipan/Boomslang другой версии не переносятся автоматически.

## Проверка описаний собственной версии

Итоговое описание связывает назначение процедуры с её инструкциями,
передаваемыми регистрами, вызывающими участками и потребителями данных.
Различия с исходным справочником сохраняются.

Примеры существенных различий и особенностей:

- По `#B044` находится иной алгоритм отсечения и вывода линий с изменяемыми
  командами и ветвями. Старые таблицы `#AFF0..#B043` сохранены, но этот
  алгоритм их не читает.
- Геометрия 23 моделей использует упакованные потоки. Нельзя автоматически
  переносить обычный формат геометрии другой Elite.
- Указатель, который попадает внутрь другой инструкции, иногда является
  действующим входом. Например, `#733E` исполняет старший байт `CALL` как
  `RST #18`.
- После `RET` встречаются живые таблицы `JP` и процедуры, доступные через
  изменяемые ветви. Они раскрываются по входящим связям, а не объявляются
  неиспользуемыми только по положению в файле.
- Игровые названия кладовских дополнений уточняются по руководству,
  извлечённому из этого же диска, и по фактическим полям состояния.

Реестры `Tools/Disasm/Reports/Semantics` содержат результаты проверки. Понятия следует
различать: точное поведение сохранённой команды можно установить, даже когда
историческая причина её присутствия не доказана. Такие ограничения
указываются прямо, предположения не выдаются за назначение автора.

## Роль SkoolKit

SkoolKit 10.1 использован как декодер инструкций Z80 и как симулятор для
изолированных проверок. Он декодирует байты пользовательского образа.
Дизассемблер сам по себе не устанавливает назначение процедур и не пишет
доказанные смысловые комментарии.

В частности, исполнением проверяются расшифровка, обмен памяти, распаковка
руководства, арифметика, экранные примитивы и рисование линий.
Лицензия SkoolKit сохранена вместе с локальной копией в `Tools/Disasm/Research/vendor/skoolkit-10.1`.
Справочный `.skool`, Python и SkoolKit не участвуют в сборке TRD.

Дополнительно проверены 2624 случая вычислителя катета `#8ACD`, 612 примеров
сохранённого арифметического хвоста `#AF64` и граничные контракты
`#FCEA/#5E78`. Исходный снимок содержит две `OUT (#0F),A` по
`#5DF3/#5DF8`, но штатный загрузчик до запуска игры заменяет обе команды
на пары `NOP`. На этом пути аппаратного вывода нет. Историческое назначение
отключённых команд не установлено, внешнее устройство им не приписывается.

## Независимые критерии проверки

| Проверка | Что она подтверждает |
|---|---|
| Покрытие исходного файла | все байты представлены кодом или явно выделенными данными |
| Сборка sjasmplus и сравнение | исходники воспроизводят семь файлов и весь исходный TRD |
| Реестр ручного разбора | для каждого фрагмента есть описание и основания его назначения |
| Аудит прямых переходов | выявлены обращения в DB и перекрывающиеся инструкции |
| Проверки симулятором | проверенные процедуры выполняют указанные операции на выбранных примерах |

Ни одна строка этой таблицы не подменяет остальные. Побайтово идентичная
сборка не доказывает правильность комментариев, а изолированные проверки
не означают прохождение всех игровых сценариев.
